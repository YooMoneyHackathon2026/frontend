# Правила для ИИ-агентов

## Область действия

Этот файл применяется к каталогу frontend и всем его подкаталогам. При добавлении других
инструкций сохраняй ссылки на них здесь и явно указывай область действия.
Вложенные AGENTS.md могут уточнять правила для соответствующих каталогов.

До нового указания пользователя работай в этой папке (`frontend/`), запускай
команды из неё и создавай файлы здесь. Здесь находится Git-корень frontend.
Соседний backend должен иметь собственный Git-корень, настройки
и отдельную пару source → destination. Не включай backend в историю фронтенда.

## OpenSpec

Изменения поведения сначала описывай в `openspec/changes/<change>/`:
`proposal.md`, `design.md`, `tasks.md`, `specs/<capability>/spec.md`.
Учитывай существующие спецификации в `openspec/specs/`.
Не отмечай реализацию завершённой до проверки сценариев; готовую документацию
не выдавай за работающий сервис. Не архивируй незавершённое изменение.

## Роль синхронизации репозиториев

Для задач копирования истории обязательно прочитай
[.agents/repository-sync.md](.agents/repository-sync.md).
Эта роль не разрабатывает продукт и не меняет его код.
Подготовка самого инструмента — отдельная задача агента реализации по OpenSpec.
Запуск, адреса репозиториев и область доступа задаёт пользователь.
Не запускай фоновую синхронизацию только из-за наличия этого файла.

## Git Flow

После клонирования выполни `npm ci` с Node 26 и авторизуй Git и GitHub CLI. Подготовка npm подключает хуки и настраивает main/develop для git-flow. Главная ветка — main. Ветки release не используются. Эмоджи запрещены в создаваемых материалах.

Для отдельной задачи обнови ссылки через `git fetch origin --tags` и создай ветку от origin/develop, например `git switch -c feature/payment-form origin/develop`. Используй feature/ для возможностей, bugfix/ для исправлений, chore/ для обслуживания. Срочное исправление начинай в hotfix/ от origin/main. Продолжение той же задачи выполняй в той же открытой ветке.

После каждого промпта с изменениями проверь результат и добавь в индекс только файлы задачи. Запусти команду публикации. Она создаёт один коммит, отправляет ветку и аннотированный тег атомарно, открывает PR при первой публикации и обновляет заголовок и общий список изменений при следующих. Для ответа без изменений пустой коммит не нужен.

    npm run tag:patch -- "feat: add payment form" "feat: Форма оплаты" "Добавлена форма оплаты"
    npm run tag:rc -- "fix: validate payment amount" "feat: Форма оплаты с проверкой суммы" "Добавлена проверка суммы"

Заголовок коммита состоит из типа, двоеточия, пробела и английского описания длиной 1–100 символов без префикса. Допустимы feat, fix, docs, style, refactor, perf, test, build, ci, chore, revert. PR имеет тот же префикс и короткий заголовок, в том числе на русском. Каждый следующий аргумент после заголовка PR — отдельный пункт описания тега. Формулируй итоговые изменения для читателя.

Первый тег задачи обычно patch, для существенного расширения выбери minor, для крупного несовместимого изменения major. Нумерация берётся из тегов репозитория. Первый patch пустой истории — v0.0.1. Версии package.json и lock-файла обновляются перед выпуском в том же коммите. На той же ветке после vX.Y.Z идут vX.Y.Z-rc.1, rc.2 и далее (по SemVer они ниже стабильной версии). Повтор публикации уже созданного тега после сетевой ошибки — `npm run tag:publish`. При коллизии тегов остановись и сверь origin, не передвигай опубликованные теги.

Обычный PR направляй в develop. Завершай принятую задачу слиянием PR, сохраняя исходную ветку. Для squash или merge укажи английский заголовок итогового коммита в формате Commitlint. В main разрешены только PR из develop, hotfix/* или chore/*. Из develop в main вручную сливает только владелец IFraimG. Агент может провести hotfix в main и затем перенести исправление через PR в develop. Прямые push в main и develop запрещены. Не запускай git flow finish и не используй опции удаления веток.

GitHub Release создаётся только для первого minor или major тега задачи. Описание перечисляет изменения с предыдущего опубликованного релиза. Сохраняй закрытые рабочие ветки и начинай новую задачу в новой ветке.
